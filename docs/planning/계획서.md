## 1. 프로젝트 개요 및 목적

### 1.1 프로젝트 주제명
**AI 자율 침투 도구(PentAGI)의 취약점 탐색 행위 탐지: Wazuh 룰 vs 행위 기반 ML 비교 검증**

### 1.2 한 줄 요약
> 시그니처 룰로는 포착되지 않는 AI 침투 도구(PentAGI)의 **"취약점 탐색 단계"**를, 단일 웹서버에서 반복 수집한 웹 로그의 행동 패턴으로 학습한 **머신러닝 모델(Random Forest)**이 탐지할 수 있는지 정량 비교 검증한다.

### 1.3 배경 및 필요성
* **기존 룰 기반 탐지의 한계:** 최근 등장한 AI 자율 침투 도구(PentAGI 등)는 고전적인 공격 문자열(SQL Injection, 명령 실행 구문 등)을 무차별 주입하지 않고, 웹 애플리케이션의 정상 비즈니스 로직과 권한 취약점(IDOR, Shadow API 등)을 지능적으로 파고듭니다. 이로 인해 방화벽이나 Wazuh 시그니처 룰셋에는 모두 정상적인 `200 OK` 요청이나 단순 미인가 요청으로만 기록되어 탐지율이 0%에 수렴합니다.
* **행위 기반 ML 접근:** 침투 도구는 사람이 웹사이트를 서핑할 때와 비교하여 **요청 속도, 시간 간격의 규칙성(표준편차), 숨은 경로 탐색 패턴(404 비율, 고유 경로 수), 자동화 User-Agent(`python-requests`)** 등에서 기계적인 행동 특성을 남깁니다. 본 프로젝트는 이 차이를 특징값(Feature)으로 추출하여 AI 모델로 선제 탐지합니다.

### 1.4 핵심 검증 가설
> **가설:** PentAGI가 취약점을 탐색하는 과정에서 남기는 로그는 Wazuh 기본 룰셋으로는 전혀 경보가 울리지 않지만(0건), 실제 수집 로그로 학습한 머신러닝 모델은 학습에 사용되지 않은 새로운 독립 공격 세션에서도 "공격 탐색 행위"임을 높은 탐지율로 분류해낼 수 있다.


### 1.5 네트워크 보안 장비(IDS/IPS, WAF) 배제 및 EDR(Wazuh) 집중 선정 이유

실무 보안에서는 침입방지시스템(IPS)과 웹방화벽(WAF)을 전면에 배치하여 악성 패킷을 실시간 차단(In-line Prevention)하는 것이 일반적입니다. 그럼에도 불구하고 본 프로젝트에서 네트워크 인라인 장비를 배제하고 **단말 EDR/로그 분석 플랫폼인 Wazuh와 행위 기반 머신러닝(ML)에만 집중한 전략적 이유**는 다음과 같습니다:

#### 1) 로직 결함 공격(IDOR, Shadow API)의 원천적 WAF/IPS 우회 특성
* **시그니처 기반 장비의 한계:** Snort, Suricata 같은 IDS/IPS와 ModSecurity 등 전통적인 WAF는 패킷 페이로드 내의 **악성 시그니처(예: `' OR 1=1`, `<script>`, 시스템 쉘 구문 등)**를 대조하여 차단합니다.
* **로직 결함의 정상 패킷 위장:** PentAGI와 최신 공격 도구가 파고드는 대상은 **IDOR(`GET /mypage.php?id=2`), 권한 검사 누락, 숨은 API 호출** 등 비즈니스 로직 취약점입니다. 이는 패킷 레벨에서 특수문자나 공격 구문이 일체 없는 **100% 정상적인 HTTP 표준 요청**이므로, 고가의 WAF/IPS를 배치하더라도 **'정상 트래픽'으로 판정하여 100% 무조건 통과(Pass)**시킵니다.
* 👉 따라서 **"어차피 WAF/IPS 시그니처로는 원천 차단이 불가능한 영역"**이므로 네트워크 장비에 의존할 수 없습니다.

#### 2) 침해 지표(IoC)의 생성 위치: 종단(Endpoint) 시스템 내부
* 공격자가 로직 결함을 찔렀을 때 발생하는 실질적인 침해 징후(타인 데이터 대량 SELECT, 비정상 파라미터 변조, PHP 런타임 Warning/Fatal Error 등)는 네트워크 전선 위가 아니라 **웹 서버 내부의 비즈니스 로그(`app.log`)와 도커 컨테이너 런타임**에서만 확인됩니다.
* 따라서 네트워크 패킷을 감시하는 IDS/IPS보다, **호스트 커널 및 애플리케이션 로그를 전수 수집할 수 있는 EDR(Wazuh Agent)**이 본 탐지 모델의 원천 데이터 수집 도구로 가장 적합합니다.

#### 3) 실무 보안 프레임워크(심층 방어 및 Assume-Breach) 반영
* 본 연구는 **"경계 방화벽(FortiGate), WAF, IPS 등 1선 시그니처 방어선은 이미 우회·돌파되었다"**고 가정하는 현대 엔터프라이즈 보안의 **'침해 가정(Assume-Breach)'** 원칙을 전제로 합니다.
* 1차 방어선이 무력화된 극한의 상황에서, **"최종 방어선인 EDR 수집 로그와 기계적 행동 패턴을 분석하는 머신러닝(Random Forest)으로 취약점 탐색 단계를 조기 포착할 수 있는가?"**라는 실제적이고 수준 높은 보안 난제를 해결하기 위해 본 아키텍처를 채택했습니다.

### 2.2 사전 확정 성공 기준 (Success Criteria)

> [!IMPORTANT]
> 본 기준은 실험 수행 전에 확정하며, 실험 결과가 가설과 다르게 나오더라도 기준을 사후 수정하지 않고 있는 그대로 보고서에 반영합니다.

2. **ML 모델 탐지 기준:** 학습에 쓰이지 않은 **독립된 테스트 세션(Unseen Test Sessions)**의 PentAGI 행위를 **탐지율 80% 이상**으로 포착하고, 정상 세션은 **오탐률 2.5% 미만(최대 5% 이내 허용)**을 유지할 것.
3. **정량 보고 지표:** 단순 Accuracy(정확도)가 아닌 **탐지율(Recall), 오탐률(FPR), 최초 탐지 시간(Time-to-Detect), 특징 중요도(Feature Importance)** 4대 지표를 산출할 것.

## 3. 인프라 아키텍처 및 네트워크 토폴로지 (FortiGate 3계층 망 분리 기반)

### 3.1 네트워크 아키텍처 및 통신 구조 개요
본 프로젝트는 엔터프라이즈 환경의 표준 보안 구성인 **WAN - DMZ - LAN 3계층 망 분리 아키텍처**를 적용합니다. 외부 노출 서비스(WEB)와 내부 핵심 자산(DB, 관제 시스템, 업무 단말)을 물리적/논리적으로 격리하고, FortiGate 경계 방화벽을 통해 트래픽을 엄격히 제어합니다.

#### 1) 주요 네트워크 영역 구성
* **외부 영역 (WAN):** 
  * 외부 인터넷 망에 해당하며, 자율 침투 공격 도구인 **공격자(ARTEX)**가 위치합니다.
* **경계 보안 영역 (Firewall):** 
  * 모든 망 간의 경계에 위치하는 **FortiGate 방화벽**이 WAN, DMZ, LAN 인터페이스 간의 트래픽을 중계하고 정책에 따라 통제합니다.
* **외부 인터넷망 (WAN):**
  * 포티넷 경계 방화벽 외부(WAN) 영역으로, 실제 이커머스 환경과 동일하게 **정상 고객 사용자**와 **공격자(ARTEX)**가 공존하여 쇼핑몰 서비스(`VIP 8000`)로 유입됩니다.
* **비무장지대 (DMZ):** 
  * 외부에서 유일하게 직접 접근이 허용되는 노출 영역으로, 공격 타겟인 **WEB 서버**만 단독으로 배치됩니다.
* **내부 업무 및 관제 영역 (LAN):** 
  * 외부 인터넷에서 직접 접근이 불가능하도록 안전하게 격리된 내부망으로, 다음 2개 노드가 위치합니다:
    * **DB 서버:** DMZ의 WEB 서버와만 데이터 질의를 위해 연동되는 핵심 데이터베이스
    * **Wazuh 관제 서버:** 전체 시스템의 로그를 중앙 집중 수집 및 분석하는 통합 보안 관제 시스템

#### 2) 서비스 트래픽 및 로그 데이터 흐름
* **외부 인입 트래픽:** 외부 정상 고객 및 공격자(ARTEX) $\rightarrow$ FortiGate 방화벽(WAN $\rightarrow$ DMZ) $\rightarrow$ DMZ의 WEB 서버로 요청 인입
* **서비스 연동 트래픽:** DMZ의 WEB 서버 $\leftrightarrow$ 내부 LAN의 DB 서버 간 데이터베이스 통신 (FortiGate 정책 기반 통제)
* **중앙 로그 수집 흐름 (점선 경로):**
  * DMZ의 **WEB 서버** $\rightarrow$ 내부 LAN의 **Wazuh** (웹 접근/에러/애플리케이션 로그 전송)
  * 내부 LAN의 **DB 서버** $\rightarrow$ 내부 LAN의 **Wazuh** (DB 쿼리/트랜잭션 로그 전송)

| **내부 LAN 망** | **통합 관제<br>(Wazuh)** | • Wazuh Manager, Indexer, Dashboard<br>• **Archives(전체 로그 `logall_json`) 활성화**<br>• 중앙 집중 통합 SIEM 관제 | • WEB, DB 전 노드의 로그를 수집·저장<br>• 외부로부터 완벽히 격리된 안전한 LAN 대역에서 관제 |

### 3.3 3대 핵심 인프라(방화벽 · 웹서버 · DB)별 전수 로그 수집 체계

Wazuh 통합 보안관제 서버(LAN)로 수집되는 대상은 **① 경계 방화벽(FortiGate), ② DMZ 웹서버, ③ LAN 데이터베이스(DB)** 3대 영역으로 분리되며, 각 장비의 계층적 특성에 따라 수집하는 로그의 종류와 머신러닝 분석 목적이 명확히 구분됩니다.

```text
[외부 트래픽] ➔ ① 경계 방화벽(FortiGate) ➔ ② DMZ 웹서버(Docker PHP) ➔ ③ LAN DB(MariaDB)
                         │                          │                         │
                   (Syslog UDP 514)          (Wazuh Agent 1514)        (Wazuh Agent 1514)
                         │                          │                         │
                         └──────────────────────────┼─────────────────────────┘
                                                    ▼
                                     [Wazuh 통합 관제 서버 (LAN)]
                                       - wazuh-archives-* (전체 로그 보관)
                                       - 머신러닝(Random Forest) 학습 데이터셋
```

#### 📊 인프라별 수집 로그 및 머신러닝/보안 분석 역할 명세

| 수집 대상 인프라 | 수집 로그 종류 | 상세 수집 경로 / 프로토콜 | 머신러닝(ML) 및 보안 관제 활용 목적 |
| :--- | :--- | :--- | :--- |

| **③ LAN DB 서버**<br>(MariaDB / MySQL) | • **일반 쿼리 로그 (General Query Log)**<br>• **슬로우 쿼리 로그 (Slow Query Log)**<br>• **DB 에러 로그 (`error.log`)**<br>• **접속/인증 로그 (Audit Log)** | Wazuh Agent 파일 수집<br>• `/var/log/mysql/general.log`<br>• `/var/log/mysql/slow.log`<br>• `/var/log/mysql/error.log` | • **로직 결함 공격의 최종 결과 검증:**<br>  - 단시간 내 비정상 다량 `SELECT` 발생 추적 (IDOR 데이터 유출 흔적)<br>  - 비정상 SQL 예외 발생 횟수 집계<br>  - DB 침투 성공 여부와 데이터 위변조 최종 판정 근거로 활용 |

> **수집 로그의 전처리 필터링 원칙:**
> 이미지(`.png`, `.jpg`), 스타일시트(`.css`), 자바스크립트(`.js`), 파비콘(`.ico`) 등 브라우저가 자동으로 대량 요청하는 정적 리소스는 웹 트래픽 통계를 왜곡하므로 머신러닝 피처 추출 단계에서 전처리 필터링(제외)하여 순수 API/PHP 요청 및 에러 데이터만 학습에 반영합니다.

### 3.4 취약점 설계 원칙 (로직 결함형 3종)
Wazuh 기본 시그니처 룰셋에는 걸리지 않고 오직 HTTP `200 OK` 정상 응답만 발생시켜 **"룰은 미탐(0건), ML은 탐지"** 가설을 검증할 수 있도록 설계합니다.

* **결함 1: IDOR (Insecure Direct Object Reference)**
  * 경로: `/mypage.php?id=2`
  * 특성: 로그인한 사용자가 파라미터 숫자만 바꾸어 타인의 개인정보/주문내역을 탈취. (정상 요청 구조)
* **결함 2: 권한 검사 누락 (Broken Function Level Authorization)**
  * 경로: `/api/admin_stats.php`
  * 특성: 일반 고객 계정 세션으로 관리자 전용 일일 매출/회원 통계 API를 직접 호출 성공.
* **결함 3: 숨은 내부 API 노출 (Shadow / Internal API)**
  * 경로: `/api/v1/internal/config.php`
  * 특성: 화면에 링크되지 않은 숨은 엔드포인트로 접근 시 내부 시스템 환경변수 및 DB 접속 설정 정보 유출.

## 4. 데이터 수집 및 라벨링 설계

### 4.1 수집 규칙 및 공정성 원칙
* **단일 서버 집중 반복 수집:** 단일 웹서버를 타겟으로 하므로, 머신러닝 학습 및 검증에 필요한 충분한 샘플 수를 확보하기 위해 **반복 세션 횟수를 확대(최소 10회 이상)**합니다.
* **수집 모드:** Wazuh Manager의 `ossec.conf`에 `<logall_json>yes</logall_json>` 설정을 통해 경보 유무와 관계없이 전체 접근 로그를 `/var/ossec/logs/archives/archives.json`에 기록합니다.

### 4.2 세션 수집 프로토콜
| 구분 | 1회 세션 길이 | 수집 방식 | 1회 세션 샘플 수 | 권장 반복 횟수 | 총 확보 샘플 수 |
| :--- | :---: | :--- | :---: | :---: | :---: |
| **정상 사용자 세션** | 10분 | 외부 WAN의 **호스트 PC/브라우저**에서 팀원이 쇼핑몰의 일반 고객 이용 시나리오(로그인, 상품 조회, 장바구니 등)를 자유롭게 수행 | 20개 창 | **10회 ~ 15회** | 200 ~ 300개 창 |
| **PentAGI 공격 세션** | 10분 | 호스트/공격 환경에서 **PentAGI**에 타겟 URL(`http://192.168.80.128:8000`)을 부여하고 자율 취약점 탐색 및 침투 수행 | 20개 창 | **10회 ~ 15회** | 200 ~ 300개 창 |

### 4.3 Wazuh 추출 원천 데이터 필드 명세 (Raw Fields)
Wazuh OpenSearch Discover(`wazuh-archives-*`)에서 머신러닝 전처리를 위해 추출 및 보관하는 핵심 필드 목록입니다:

| 필드명 (JSON Key) | 타입 | 실제 수집 데이터 예시 | 추출 목적 및 ML 활용 |
| :--- | :---: | :--- | :--- |
| **`timestamp`** | String (ISO) | `2026-10-26T06:18:26.984+09:00` | 30초 시간 윈도우 분할, 요청 간격(`interval_mean/std`) 산출 |
| **`data.client_ip`** | String (IP) | `192.168.80.135` | 세션/클라이언트 식별 및 정답 라벨링 (`Label=1` or `0`) |
| **`data.method`** | String | `GET`, `POST` | `ratio_post` (POST 메서드 비율 산출) |
| **`data.path`** | String | `/api/v2/profile/10001` | `req_count` (요청 빈도), `unique_url_count` (고유 경로 탐색 수) |
| **`data.status`** | Integer | `404`, `200`, `500` | `error_404_ratio` (숨은 경로 탐색 에러율), `500` 서버 에러율 |
| **`data.response_bytes`**| Integer | `48`, `4521` | `bytes_mean` (응답 크기 평균 통계) |
| **`data.duration_ms`** | Float | `2.0`, `15.4` | 서버 처리 지연 시간 |
| **`data.user_agent`** | String | `python-requests/2.32.3` | 도구 자동화 지표 식별 (`unique_ua_count`) |
| **`data.user_id`** | String/Null | `null`, `user_1` | 인증 우회 및 미인가 파라미터 조작 식별 |

> [!NOTE]
> **경계 방화벽(FortiGate) Syslog 수집 배제에 대한 아키텍처적 근거:**  
> 위 표에서 보듯 머신러닝의 8대 행동 특징값(`path`, `status`, `user_agent`, `method` 등)은 모두 **L7 애플리케이션 레벨의 정보**입니다. 경계 방화벽이 남기는 L3/L4 트래픽 로그(IP/Port/Bytes)에는 URL 경로와 HTTP 응답 코드가 전혀 존재하지 않아 모델 학습 피처로 활용이 불가능합니다. 오히려 수많은 TCP 세션 연결/종료 로그가 유입될 경우 시간 윈도우 집계 시 데이터 편향(Noise)을 유발하므로, 관제 및 학습 데이터 파이프라인에서 방화벽 로그를 배제하고 웹서버/DB 로그에 집중하는 것이 데이터 품질과 모델 신뢰성 측면에서 가장 최적화된 설계입니다.

## 5. 머신러닝(Random Forest) 파이프라인 및 학습 계획 (세션 단위 분할)

### 5.1 End-to-End 머신러닝 파이프라인
```
[1. 원본 로그 수집]
   Wazuh archives.json (Apache access_log, app_auth.log 등)
       │
       ▼
[2. 세션 매핑 및 전처리]
   실험 기록표 대조 ➔ 세션 ID 및 라벨(정상=0, PentAGI=1) 부여
       │
       ▼
[3. 시간 창 분할 및 8대 특징값(Feature) 추출]
   IP별로 30초 단위 슬라이딩 윈도우 생성 ➔ 8개 통계 숫자 벡터로 변환
       │
       ▼
[4. 세션 단위 데이터셋 분할 (Session-based Split)]
   • 학습 데이터셋 (Train Set): 세션 1 ~ 8회차 (전체의 약 70~80%)
   • 검증 데이터셋 (Test Set) : 세션 9 ~ 10회차 (완전히 독립된 미지의 20~30% 세션)
       │
       ▼
[5. Random Forest 모델 학습]
   100개의 Decision Tree가 행동 리듬(간격 표준편차, 404비율 등)을 학습하여 투표 판정
   (※ XGBoost, 로지스틱 회귀, Isolation Forest는 7장 선택 과제로 배치)
       │
       ▼
[6. 정량 평가 및 특징 중요도(Feature Importance) 분석]
   Wazuh 룰 탐지 결과와 1:1 대조 및 XAI(설명 가능한 보안 리포트) 도출
```

### 5.2 8대 핵심 행동 특징값(Feature Engineering) 정의

| 번호 | 특징값 변수명 | 계산 방식 (IP별 30초 창 기준) | 정상 vs PentAGI 간 노리는 행위 차이 |
| :---: | :--- | :--- | :--- |
| **1** | `req_count` | 30초 창 내 총 HTTP 요청 수 | 도구는 사람보다 짧은 시간에 훨씬 많은 요청을 전송 |
| **2** | `interval_mean` | 연속된 요청 간 시간 간격의 평균 (초) | 도구는 연속 요청 간 딜레이가 극히 짧음 |
| **3** | `interval_std` | 연속된 요청 간 시간 간격의 표준편차 | 사람은 불규칙적(큰 편차), 도구는 기계적/규칙적(작은 편차) |
| **4** | `error_404_ratio` | 404 Not Found 응답 수 / 총 요청 수 | 취약 경로를 무작위 탐색하는 과정에서 404 비율 급증 |
| **5** | `unique_url_count` | 30초 내 접근한 서로 다른 URL의 고유 개수 | 공격 도구는 짧은 시간에 다양한 엔드포인트를 광범위하게 찌름 |
| **6** | `unique_ua_count` | 서로 다른 User-Agent 문자열의 개수 | 도구가 분석 회피를 위해 헤더를 변조하거나 `python-requests` 고정 여부 감지 |
| **7** | `bytes_mean` | 응답 크기(Bytes)의 평균값 | 에러 페이지, JSON 응답, 정상 HTML 간의 크기 통계 차이 |
| **8** | `new_path_ratio` | 미식별 경로 요청 수 / 총 요청 수 | 정상 베이스라인에 등록되지 않은 숨은 API/경로 탐색 비율 |

### 5.3 단일 웹서버 환경에서의 데이터 분할 전략: 세션 단위 분할 (Session-based Split)

> [!WARNING]
> **단순 무작위(Random) 셔플 분할 금지 (데이터 누수 방지)**
> 단일 웹서버 환경에서 30초 창들을 무작위(Random)로 섞어 Train/Test로 나누면, **동일한 공격 세션 내의 앞뒤 창들이 섞여 들어가 미래의 정보를 미리 엿보는 데이터 누수(Data Leakage)**가 발생합니다. 이 경우 모델 성능이 100%로 과대평가됩니다.

* **세션 단위 분할 원칙 (Group/Session Split):**
  * **학습 세트 (Train Set):** 앞선 1회차 ~ 8회차 세션에서 발생한 모든 30초 창 샘플
  * **테스트 세트 (Test Set):** 학습에 전혀 참여하지 않은 **독립된 9회차 ~ 10회차 세션(Unseen Sessions)**의 30초 창 샘플
  * 👉 **의의:** 단일 웹서버 환경이더라도, 모델이 특정 시점의 IP나 직전 요청을 외운 것이 아니라 **새롭게 시작된 독립적인 PentAGI 세션을 스스로 잡아낼 수 있는지(일반화 성능)**를 학술적으로 완벽하게 입증할 수 있습니다.

### 5.4 파이썬 기반 학습 및 평가 코드 구조

```python
import pandas as pd
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import classification_report, confusion_matrix
import joblib
import matplotlib.pyplot as plt

# 1. 전처리된 특징값 데이터셋 로드 (session_id 포함)
df_features = pd.read_csv("dataset_features_with_session.csv")

feature_cols = [
    'req_count', 'interval_mean', 'interval_std', 
    'error_404_ratio', 'unique_url_count', 'unique_ua_count', 
    'bytes_mean', 'new_path_ratio'
]

# 2. 세션 단위 분할 (예: 1~8회차 학습, 9~10회차 독립 테스트)
train_sessions = ['session_01', 'session_02', 'session_03', 'session_04', 
                  'session_05', 'session_06', 'session_07', 'session_08']
test_sessions  = ['session_09', 'session_10']

df_train = df_features[df_features['session_id'].isin(train_sessions)]
df_test  = df_features[df_features['session_id'].isin(test_sessions)]

X_train, y_train = df_train[feature_cols], df_train['label']
X_test, y_test   = df_test[feature_cols], df_test['label']

# 3. Random Forest 모델 정의 및 학습
model = RandomForestClassifier(n_estimators=100, max_depth=10, random_state=42)
model.fit(X_train, y_train)

# 4. 모델 저장 (오프라인 검증용)
joblib.dump(model, "models/pentagi_detector_rf.pkl")

y_pred = model.predict(X_test)
print(confusion_matrix(y_test, y_pred))
print(classification_report(y_test, y_pred, target_names=['정상(0)', 'PentAGI(1)']))

# 6. 특징 중요도(Feature Importance) 분석 및 시각화
importances = pd.Series(model.feature_importances_, index=feature_cols).sort_values(ascending=True)
```

## 6. 정량 평가 및 Wazuh 룰 비교 검증 지표

10분 세션을 30초 단위로 분할하면 **세션당 20개의 창(Sample)**이 생성됩니다. 룰과 ML은 동일 세션에 대해 아래 4대 지표로 직접 대조 평가됩니다.

### 6.1 4대 정량 비교 평가 지표

| 평가 항목 | Wazuh 기본 룰셋 측정 방식 | Random Forest 모델 측정 방식 | 비고 및 목표치 |
| :--- | :--- | :--- | :--- |
| **① PentAGI 탐지율**<br>(Recall) | 공격 세션 내 웹 공격 관련 기본 경보 발생 건수 (유/무) | $\frac{\text{공격으로 올바르게 판정한 창 수}}{\text{전체 PentAGI 창 수 (20개)}} \times 100$ | **ML 목표: 80% 이상**<br>(Wazuh 룰 0% 미탐 대비 우위 입증) |
| **② 정상 세션 오탐률**<br>(FPR) | 정상 사용 중 오발령된 경보 건수 | $\frac{\text{공격으로 잘못 오인한 창 수}}{\text{전체 정상 창 수 (20개)}} \times 100$ | **ML 목표: 2.5% 미만**<br>(최대 5.0% 이내 통제) |
| **③ 최초 탐지 소요 시간**<br>(Time-to-Detect) | 세션 시작 후 첫 번째 경보 발생 시각까지 소요 초 | 세션 시작 후 첫 번째 이상(1) 판정이 나온 창의 시작 초 | **ML 목표: 30~60초 이내**<br>(피해 발생 전 조기 경보) |
| **④ 판정 근거 제시력**<br>(XAI 설명 가능성) | 매칭된 시그니처 룰 ID 및 룰 설명문 | 판정에 가장 크게 기여한 **특징 중요도 Top 3** 제시 | "왜 공격으로 판정했는가"에 대한 정량적 보안 근거 확보 |

### 6.2 최종 결과 보고서 비교표 양식 (Expected Result)

| 비교 항목 | Wazuh 기본 룰셋 (시그니처) | 학습된 Random Forest 모델 (행위 기반) | 비교 검증 시사점 |
| :--- | :---: | :---: | :--- |
| **PentAGI 세션 탐지율** | **0.0%** (0건 미탐) | **85.0% ~ 95.0%** (포착 성공) | 로직 결함을 찌르는 AI 공격을 행위 통계로 탐지 성공 |
| **정상 세션 오탐률** | 0.0% | **2.5% 미만** | 일상적인 웹 서핑 트래픽을 공격자로 오인하지 않음 |
| **최초 탐지 시간** | - (미탐으로 측정 불가) | 공격 개시 후 **30~60초 이내** | 데이터 대량 탈취나 권한 상승 전 조기 경보 가능 |
| **판정 근거** | 없음 | 특징 기여도 (`interval_std`, `error_404_ratio` 등) | 행위 기반 XAI를 통한 납득 가능한 보안 리포트 제시 |
